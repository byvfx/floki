# Floki v1.13.3 — field test

> Released 31 Aug 2026 (UTC) · tag `v1.13.3` · `main` @ `dcdd28d` · [release page](https://github.com/byvfx/floki/releases/tag/v1.13.3)

What's worth banging on in this release, what's already known, and what to send
back. This is the v1.13.0 feature set — 29 changes across Added / Fixed /
Changed, concentrated in **playback, cache and layer geometry** — plus two
rounds of hotfixes that dogfooding turned up, all of them in **precache**:

- **v1.13.1** — precache was dead on layer stacks
  ([#296](https://github.com/byvfx/floki/issues/296)): the fill declared itself
  finished with one frame barely in flight.
- **v1.13.2** — three more. The fill ignored **visibility and solo** changes
  ([#319](https://github.com/byvfx/floki/issues/319)), it **stopped at a
  thirtieth of the RAM budget** and stayed there until you pressed Play
  ([#322](https://github.com/byvfx/floki/issues/322)), and the read-ahead warmer
  was doing blocking filesystem work on the UI thread on networked media
  ([#309](https://github.com/byvfx/floki/issues/309)).

- **v1.13.3** — mostly **subtraction**. Two subsystems that could not run were
  removed: the GPU texture pre-upload ring, which built a full-res texture every
  playback frame into a cache nothing read
  ([#299](https://github.com/byvfx/floki/issues/299)), and the old "base track"
  layer path ([#301](https://github.com/byvfx/floki/issues/301)). Plus two cache
  fixes for hiding the layer that drives playback
  ([#325](https://github.com/byvfx/floki/issues/325),
  [#329](https://github.com/byvfx/floki/issues/329)).

Test on **v1.13.3**; heavy sequences are where the value is.

**The runs below are unchanged from the v1.13.2 guide, deliberately.** Nothing
in v1.13.3 alters what they exercise — it removes dead code and fixes two cache
bugs that misbehaved silently. If you already ran them on v1.13.2, the useful
thing now is run 1 (does playback still look and feel right?) and run 5, not a
full pass.

**One visible change:** the **GPU cache** checkbox is gone from the transport
row. It pre-uploaded frames to GPU textures — except nothing ever read them, so
it was spending 20–60 ms of every frame building textures that could not be
displayed. Turning it *off* was always the faster setting. Nothing replaces it;
there is simply less work per frame now.

## Get the build

Grab a binary from the [v1.13.3 release page](https://github.com/byvfx/floki/releases/tag/v1.13.3),
or paste a command. Each one is self-contained with OpenColorIO built in — no
install, no dependencies, nothing to unpack.

**Windows** — x86_64, 38 MB

```powershell
curl.exe -LO https://github.com/byvfx/floki/releases/download/v1.13.3/floki-windows-x86_64.exe
.\floki-windows-x86_64.exe shot.0001.exr
```

**macOS** — Apple Silicon only, 34 MB

```bash
curl -LO https://github.com/byvfx/floki/releases/download/v1.13.3/floki-macos-arm64
chmod +x floki-macos-arm64
./floki-macos-arm64 shot.0001.exr
```

**Linux** — x86_64 / glibc, 52 MB

```bash
curl -LO https://github.com/byvfx/floki/releases/download/v1.13.3/floki-linux-x86_64
chmod +x floki-linux-x86_64
./floki-linux-x86_64 shot.0001.exr
```

### Two things that will trip you up

- **There's no executable bit.** Release assets are stored as plain files, so
  macOS and Linux downloads arrive non-executable — `chmod +x` or you get
  "permission denied".
- **The binaries are unsigned.** Downloading through a *browser* quarantines
  them: on macOS clear it with `xattr -d com.apple.quarantine floki-macos-arm64`;
  on Windows SmartScreen shows "More info → Run anyway". `curl` sets no
  quarantine attribute, which is why the commands above are the shorter path.

## What to try

Numbered so you can say "run 4 looked wrong" without describing the whole thing.
Runs 4 and 5 are the precache work (v1.13.1/v1.13.2, refined in v1.13.3); 1–3
are the v1.13.0 cache work and still worth a pass. The rest are quicker checks.

### 1. Heavy sequence playback — the main event

- **Do** — open a **multi-part** sequence (Karma/Houdini, one AOV per part),
  press Play, open the playback debug overlay. Let it loop a few times.
- **Should see** — the T1 row reporting a cap **sized from a measured frame**,
  not sitting at the default. The cache bar under the scrubber filling and
  staying filled. The fps readout showing a real number — **never 0.0** while
  playing.
- **Why** — six separate cache fixes landed here: bytes budget enforced
  alongside frame count, resident bytes measured rather than assumed, and a RAM
  budget that was running ~10× under-used on heavy multi-part renders.

### 2. Press Play on an already-cached range

- **Do** — let a range cache while paused (watch the bar fill), then hit Play.
- **Should see** — the cached span **does not shrink** when playback starts. It
  used to.

### 3. Pause, wait, resume

- **Do** — play, pause for 30 seconds or so, then resume. Watch the frame-time
  percentiles in the overlay across the pause.
- **Should see** — percentiles **unaffected by the idle span**; the pause
  shouldn't be filed as one enormous frame time. Read-ahead should survive the
  pause on comp layers rather than being thrown away.
- **Why** — this is the class of bug the automated suite structurally cannot
  catch, because the trigger is human timing. Worth doing by hand.

### 4. Precache on a layer stack — the hotfix runs

- **Do** — build a stack of two or three **sequence layers** (no plate in
  slot A, so the stack drives the clock). Turn **Precache** on once, then keep
  your hands off. When the bar settles, delete the stack, load a different
  one, and keep your hands off again.
- **Should see** — the cache bar under the scrubber walking to the RAM budget
  **on its own**, both times — no checkbox flipping, no pressing Play to kick
  it. Once the bar stops, scrubbing anywhere in the range is instant.
- **Why** — v1.13.0 shipped with precache dead on exactly this setup: the fill
  declared itself finished with one frame barely in flight, and every re-tick
  of the checkbox bought exactly one more frame. A rebuilt stack also
  inherited the stale "filled" verdict from the footage that was no longer
  loaded, so nothing cached until the playhead moved. Both fixed in v1.13.1
  ([#296](https://github.com/byvfx/floki/issues/296)). Human-timing-shaped —
  the suite can't see checkbox flips — so a hands-on pass here is the real
  regression check.

### 5. Precache, the rest of the way — new in v1.13.2

Three separate ways the fill used to stop early. All of them want the clock
**stopped** and your hands **off** — pressing Play restarts the fill by another
route and hides every one of these.

- **Do (a)** — with the stack precaching, **hide** a layer, let the bar settle,
  then **un-hide** it. Same again with **solo**: solo one layer, let it settle,
  then clear the solo.
- **Should see** — the bar starting to move again on its own each time you bring
  a layer *back*. Hiding is the quiet direction; un-hiding is the one that used
  to do nothing at all until the playhead moved
  ([#319](https://github.com/byvfx/floki/issues/319)).

- **Do (b)** — just let it fill, and watch how far it gets against the RAM
  figure in the playback debug overlay.
- **Should see** — the cache bar walking to **the budget**, not stopping a
  fraction of the way in. The stall this replaces was stark: 26 frames, 2.8 GB
  of a 28.4 GB budget, then nothing until a Play
  ([#322](https://github.com/byvfx/floki/issues/322)). If the bar stops well
  short of the RAM you've given it and stays stopped, that's the bug back —
  grab a log.

- **Do (c)**, on **networked storage** only — play a range you have already
  cached to disk (the on-disk proxy cache), and watch the frame-time
  percentiles.
- **Should see** — no periodic hitching from the read-ahead warmer. It used to
  stat the source file twice and the cache file once **on the UI thread** for
  every frame it considered warming, which is milliseconds each on a share and
  invisible on a local NVMe ([#309](https://github.com/byvfx/floki/issues/309)).
  This is the one run where local disk tells you nothing.

### 6. Overload it deliberately

- **Do** — open the heaviest footage you have with **Beauty preview off and
  Scrub proxy off**, then play.
- **Should see** — after about two seconds, a hint in the transport row:
  `Decode-bound: 691 ms/frame vs 41 ms needed`, sitting right next to the two
  settings that fix it. Non-modal, dismissible until the next seek.

### 7. Anamorphic and overscan geometry

- **Do** — composite an anamorphic layer with a spherical one. Try the per-layer
  pixel-aspect override. Check the display-resolution readout and the overscan
  overlay.
- **Should see** — each layer keeping **its own** aspect rather than being forced
  to the base layer's. The overscan overlay stating how much overscan there is.
  The composite not clipping to any one layer's rect.

### 8. Open a file that's already open

- **Do** — open a file, then open the same path again. Menu, drag-drop and
  recent-files all count.
- **Should see** — it **focuses the existing layer**. No second invisible copy in
  the stack.

### 9. Reset settings

- **Do** — flip a few playback toggles, then Help → **Reset playback settings**.
- **Should see** — decode and memory levers back at defaults, while your
  **layers, recent files and colour setup survive**. It's meant to be safe to
  reach for mid-session.

### 10. GPU reporting

- **Do** — just launch it and read the log. Especially valuable if your GPU is
  old, virtualised, or a laptop iGPU.
- **Should see** — a line naming **which GPU it picked**. If the GPU genuinely
  can't run Floki, a clear message saying so instead of a crash or a black frame.

## Caveats

Known and expected. None of these are worth a bug report.

| Thing | What to expect |
|---|---|
| **Single-part EXRs on Apple Silicon** | Decode runs **1.8–2.9× slower than OpenEXR** across every codec, worst on PIZ and DWA. Multi-part is fine — competitive or faster. Pre-existing and tracked in [#33](https://github.com/byvfx/floki/issues/33), not from this release. **Use multi-part footage for any performance read on a Mac** — see [`docs/perf/dwa-arm-decode-investigation.md`](../perf/dwa-arm-decode-investigation.md). |
| **macOS architecture** | Apple Silicon only. There is no Intel build in the matrix. |
| **Unsigned binaries** | No code-signing or notarisation yet. Gatekeeper and SmartScreen will object to a browser download; see above. |
| **Version reported** | Should read **1.13.3**. Anything older predates the precache fixes — run 4 fails on 1.13.0, run 5 fails on 1.13.1 — so re-download from the release page rather than reporting either. |

## Already known — please don't file these

Open, reproduced, and tracked. A "me too" on the existing issue is useful; a
duplicate isn't.

| Issue | |
|---|---|
| [#206](https://github.com/byvfx/floki/issues/206) | **Crash when closing after a long idle session.** Main-thread stack overflow on quit. Leave it open a long while, close it, and you may well hit this — it is the one you are most likely to run into. |
| [#262](https://github.com/byvfx/floki/issues/262) | **Wipe and Diff stretch one layer to the other's geometry.** The *composite* path handles per-layer geometry correctly — that is what run 7 exercises — but a 2-input draw still has only one rect, so Wipe and Diff between differently-shaped layers still distort. Expected for now. |
| [#240](https://github.com/byvfx/floki/issues/240) | **Comp contact sheet shows the open-time frame, not the played one.** The thumbnails are pinned to the decode at open and never follow the playhead. |
| [#252](https://github.com/byvfx/floki/issues/252) | **Beauty preview's tooltip is stale.** The text describes behaviour from before the per-AOV decode work. The switch itself is close to obsolete. |

## Reporting something

Open an issue at [github.com/byvfx/floki/issues](https://github.com/byvfx/floki/issues).
For anything playback- or cache-related, a log makes the difference between a
guess and a diagnosis:

```bash
# macOS
RUST_LOG=floki=debug ./floki-macos-arm64 shot.0001.exr 2> floki.log
```

```bash
# Linux
RUST_LOG=floki=debug ./floki-linux-x86_64 shot.0001.exr 2> floki.log
```

```powershell
# Windows PowerShell
$env:RUST_LOG = "floki=debug"; .\floki-windows-x86_64.exe shot.0001.exr 2> floki.log
```

That emits a once-per-second playback trace carrying `t1=`, `size_bytes=`,
`t1_bytes=<resident>/<budget>`, `evict=` and `fallback=` — exactly the state
needed to tell a mis-sized cache from a slow disk.

Added in v1.13.2, and the two fields worth quoting if the fill stops early:
`size_src=` names which fidelity the cache sized itself from (`proxy`, `beauty`,
`full` or `fallback`), and `size_prov=1` means that figure is a stand-in for one
that hasn't been measured yet. `size_src=beauty` next to a full-frame
`size_bytes` is what identified [#322](https://github.com/byvfx/floki/issues/322)
in a single line, so it is the first thing to look at.

### Worth including

- OS and GPU. The GPU is now named in the log, so the log covers it.
- Whether the footage is **single-part or multi-part**, and roughly its
  resolution and per-frame size. This distinction drives most performance
  behaviour.
- Which of Beauty preview, Scrub proxy and Precache were on.
- The run number above, if it was one of those.

### Especially wanted

Anything where **playback is smooth on one machine and not another** with the
same footage, and anything involving a **pause or a long idle**. The automated
suite is structurally blind to human timing — a bug of that shape once survived
360 passing tests and a dozen clean soak runs (#236) — so this is the category
where hands-on testing genuinely finds what nothing else can.

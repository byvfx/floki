# Floki Codebase Audit — July 2026

Follow-up to [audit-2026-06.md](audit-2026-06.md), focused on **playback
responsiveness** (the stated goal), **performance**, and **maintainability**.
Four parallel deep-dives: the decode/cache hot path, the GPU render path, the
UI-thread frame budget, and architecture. The four highest-severity findings
were verified by hand at the cited lines.

Each finding is tracked as a GitHub issue; this document is the single source
those issues reference.

**Headline: playback is architecturally sound — no locks on the frame path,
correct epoch supersession, a well-designed T1/T2 tier split — but four small,
verified defects are collectively costing large fractions of the achievable
frame rate.** All four are S/M-effort fixes. Below them sits one big theme
(the texture-upload path does roughly 2–4× the necessary work per frame) and
one big maintainability move (extract the playback engine out of `ExrApp`
before the Qt port).

Status of the June audit: held up well. `ExrViewer::ui()` stayed a ~228-line
orchestrator, tests grew 61 → ~239, feature-flag sprawl is gone (OCIO is
mandatory since #121), and the texture-gen sibling family collapsed with the
CPU path removal (#59). The regressions are new growth, not backsliding.

## Part 1 — Playback responsiveness: the four verified defects

These are ordered by expected impact. All were confirmed at the cited lines,
not just reported by the sweep.

### P1. Decode results sit unread in the channel for up to 50 ms — `src/app.rs:907`, `src/app.rs:2183`

The decode worker sends `LoadMsg` over the result channel but has no
`egui::Context`, so it cannot wake the UI; the UI discovers results only at
its next repaint, which while a decode is in flight is the 50 ms poll
(`request_repaint_after(50ms)`, app.rs:2183). Every decode-bound frame and
every scrub landing pays a 0–50 ms delivery tax **on top of** decode time —
and because the pump keeps one job outstanding, the worker idles during that
window too. When decode time is comparable to the poll interval this roughly
halves effective decode throughput.

**Fix (S):** clone the `egui::Context` into the worker thread in
`ensure_worker` and call `ctx.request_repaint()` after each `result_tx.send`.
Keep the 50 ms poll as a fallback only.

### P2. The frame clock systematically runs below target fps — `src/app.rs:1400`, `src/app.rs:1407`

`tick_playback` schedules the next wake at `now + period` rather than at the
next deadline `anchor + n·period`, and `tick_stutter` advances at most one
frame per wake. Each cycle therefore takes `period + wake_slop` (timer/vsync
quantization), and the anchor's drift correction can't compensate: once lag
exceeds one period, the code **re-anchors and forgets the lag** (app.rs:1422)
instead of catching up. Net effect: a 24 fps target on a 60 Hz display wakes
roughly every 50 ms → ~20 fps even with every frame cache-resident.
`measured_fps` should confirm this directly.

**Fix (S):** schedule `request_repaint_after(due.saturating_duration_since(now))`
using the real deadline; optionally allow stutter a bounded catch-up burst of
already-resident frames before re-anchoring. Note this interacts with #100's
validation numbers — the hardening doc's "0.6/24 fps — pacing path confirmed
correct" is partly this defect plus P1, not pure decode throughput.

### P3. Holding the scrubber still livelocks the decode of the held frame — `src/app.rs:3497`, `src/app.rs:1233`, `src/app.rs:1203`

`resp.dragged()` is true on every egui frame while the mouse button is held,
even stationary, and `draw_timeline` calls `playback_scrub_to(frame)`
unconditionally. `playback_scrub_to` unconditionally calls
`invalidate_inflight()` — an epoch bump — even when the target equals
`current_frame` and is already pending. So every UI frame supersedes the
decode submitted the frame before; when that decode completes,
`apply_load_result` drops it (`res.epoch != playback.epoch`) **before the T1
insert**. The held frame is decoded in a loop and never displayed or cached
until the mouse is released. This is the surviving instance of the scrub-flood
pattern that 443868e fixed on the worker side (queued-job skip); the completed
result drop was the other half. Side effect: `precache_filled` is re-cleared
every held frame, re-kicking precache churn.

**Fix (S):** in `draw_timeline`, only call `playback_scrub_to` when the
computed frame differs from `playback.current_frame`; belt-and-braces, early
return in `playback_scrub_to` when `next == current_frame &&
playback.pending == Some(next)`.

### P4. Loop-wrap prefetch is evicted on arrival — decode churn and a guaranteed stutter at every wrap — `src/cache.rs:151`, `src/scheduler.rs:43`

`next_want` correctly wraps the prefetch window past the out point in Loop
mode, but `pick_victim`'s "behind" test is a plain `frame < playhead` with
absolute distance (cache.rs:167). With the playhead near the out point, a
just-decoded wrapped frame (frame 1 at playhead 98) has near-maximal
evictability, so `evict_to` evicts it immediately after insert and the pump
re-requests it — the worker spins re-decoding the wrapped frames until the
playhead wraps, and the wrap itself lands on a cache miss. This falsifies the
scheduler's stated invariant that the window "never reaches past the cache
horizon to a frame that would be evicted and re-requested forever," whenever
`frame_cache_cap < range length` (the normal case for heavy footage).

**Fix (M):** during Loop play, measure distance in the play direction modulo
the in/out span (`fwd = (frame - playhead).rem_euclid(len)`); treat
`fwd <= prefetch_depth` as ahead and evict max-`fwd` first. Ping-pong:
distance along the bounce path. Add a loop-boundary regression test. Same
defect class exists in `t2_victim` (viewer.rs:247), low impact at cap ≤ 8.

## Part 2 — The texture-upload path (one theme, several multipliers)

The per-frame CPU cost during playback is dominated by `build_layer_texture`
(viewer.rs:2889) and its callers. Four independent multipliers stack:

### U1. Frames upload as Rgba32Float — 2× bandwidth and VRAM for f16 sources — `src/viewer.rs:2944`

EXR beauty data is overwhelmingly f16, but every layer texture is packed and
uploaded as RGBA32F: ~132 MB per 4K frame, times the T2 ring in VRAM, times up
to two uploads per UI frame. The shader does f32 math regardless.
**Fix (M):** pack to `Rgba16Float` (lossless for f16 sources; keep 32F only
when a source channel is f32/u32). Bonus: 16F is filterable everywhere, which
unlocks a linear sampler for the main image (currently Nearest — minification
shimmer during zoomed-out playback, gpu/mod.rs:459).

### U2. F16 sources take the slow per-pixel path in the pack — `src/viewer.rs:2902`, `src/viewer.rs:64`

The pack hoists only `&[f32]` slices; f16 channels fall back to per-pixel enum
dispatch + bounds-checked index + scalar `to_f32` — ~32 M samples per 4K build
on the UI thread. This is the hottest per-frame CPU cost for half-float
sequences. **Fix (S):** add an f16 fast path (row-wise
`convert_to_f32_slice`, or direct f16 pack once U1 lands).

### U3. Fresh ~132 MB `Vec` allocated and page-faulted per build — `src/viewer.rs:2900`

Continuous large-allocation churn during playback; repeated commit/decommit of
100+ MB regions is a known Windows stutter source (adjacent to the 443868e
freezes). **Fix (S):** reusable per-viewer staging buffer; reuse
same-dimension textures via `write_texture` instead of create-per-build.

### U4. `pump_t2` budgets by count (2 builds/frame), not bytes/time — `src/app.rs:1168`

Two 4K builds is 20–60 ms of UI-thread stall in one frame; fine at 2K, a
hiccup generator at 4K+. On a T2 miss the same work runs synchronously inside
`ui()` before paint (viewer.rs:1944). Also: `pump_t2` allocates its want-list
Vec+HashSet every frame even when the ring is full — add an early-out.
**Fix (S):** byte/time budget (~1 build or ~4 ms at 4K). **Longer term (M):**
pack on the decode worker so the UI thread only does `write_texture`.

## Part 3 — Other per-frame costs on the UI thread

### F1. Full-res histogram recomputed every playback frame while the side panel shows it — `src/app.rs:1822`, `src/viewer.rs:3501`

`swap_image_arc` invalidates the histogram key on every frame swap;
`draw_side_panel` then recomputes a full-image rayon scan (~8 M pixels at 4K)
inside `update()` at playback rate, contending with decode and the texture
pack for the global rayon pool. **Fix (S):** skip while
`sampling_suppressed()`, recompute on settle (mirrors the readout
suppression).

### F2. Scrubbing decodes full all-AOV frames — `src/app.rs:1071`

`decode_beauty_only` returns false while paused, and scrubbing is `Paused` —
so every scrub position pays a full `ExrData::load` even though the settle-
upgrade machinery already exists to restore full res on release. This is
independent of (and cheaper than) #94's on-disk proxies. **Fix (S/M):** treat
an active scrub (pointer down on the timeline) like playing in
`decode_beauty_only`; `settle_to_full` already handles the upgrade.

### F3. Contact sheet open during playback re-bakes every layer thumbnail every frame swap — `src/viewer.rs:1737`, `src/gpu/thumbnail.rs:205`

Per swap: all A-thumbnails invalidated, then regenerated in one frame — per
layer a CPU decimate, texture create/upload, an encoder with an **individual
`queue.submit`**, and a `renderer.write()` lock. 40-AOV EXR = 40 renders per
playback frame. **Fix (M):** skip thumbnail invalidation while playing
(regenerate on settle); batch thumbnail passes into one encoder/submit;
amortize N cells/frame, visible first.

### F4. Render-watch does synchronous `read_dir` + per-file `stat` in `update()` — `src/app.rs:1484`, `src/sequence.rs:250`

Every 2 s while Watch is on — on a network share (the actual use case) a
periodic multi-hundred-ms hitch mid-playback. **Fix (M):** background thread +
`ScanDiff` channel; `rescan_and_apply` is already pure enough to relocate.

### F5. Smaller (S each)
- **Blink mode** spams unconditional `request_repaint()` every frame →
  compute time-to-next-flip and use `request_repaint_after` (viewer.rs:1603).
- **Snapshot finalize** (clipboard + PNG encode/write) is synchronous in the
  frame that receives the screenshot — move to a spawned thread (app.rs:757).
- **Overscan dim** draws the full image quad twice per repaint in the
  non-OCIO path (default `overscan_opacity=0.2`) — fold the dim factor into
  the shader like the OCIO blit already does (viewer.rs:2871). (M)
- **`swap_image_arc`** invalidates textures + histogram even when handed the
  already-displayed `Arc` (scrub-return, settle) — `Arc::ptr_eq` early-out
  (app.rs:1794).
- **Timeline cache strip** paints one rect per resident T1 frame per repaint —
  coalesce contiguous runs (app.rs:3450).
- **T1 cap shrink isn't enforced until the next decode lands** — with precache
  latched, external memory pressure lowers the cap but nothing evicts. Call
  `evict_to` from the cap recompute (app.rs:2784, contract-relevant).
- **Histogram/diff state clones** round-tripped app↔viewer per frame
  (app.rs:3848) — see M3 below, same root cause.

## Part 4 — GPU correctness (non-perf)

- **G1. GPU thumbnails go stale on LUT toggle/reload** — `enable_lut` + LUT
  contents are baked into cached thumbnails, but neither the checkbox
  (app.rs:2594) nor `apply_lut_load_result` (app.rs:782) invalidates them.
  Every other baked input (exposure/gamma/sRGB/channel) does. Fix (S): LUT
  signature check like `gpu_thumb_bg`, or `invalidate_tone` from both sites.
- **G2. `OcioTargets::drop` force-destroys textures — the #120 pattern** —
  safe today only by implicit call-site ordering (gpu/ocio_pass.rs:331,
  resources.rs:90). T2 eviction deliberately chose drop-only for this exact
  reason. Fix (S): switch to drop-only, or assert the ordering invariant.
- **G3. Thumbnail generators share uniform-ring slot 0 with the viewport**
  (gpu/thumbnail.rs:160 vs viewer.rs:2531) — safe only while sheet and canvas
  are mutually exclusive. Fix (S): reserve dedicated slots.
- **G4. `pending_thumb_frees` drains only when the sheet is drawn**
  (viewer.rs:1679) — stale generation held in VRAM until the sheet reopens.
  Fix (S): drain once per frame in `ui()`.
- **G5. OCIO blit shows a never-rendered display texture while the config
  loads** (gpu/ocio_pass.rs:544) — transient background flash. Fix (S): skip
  blit when `last_render_sig.is_none()`.
- **G6. Uniform-ring overflow is `debug_assert`-only** (viewer.rs:2533) —
  will matter when #104's N-way compare lands. Fix (S): saturate + log, or
  size the ring from the render program.

## Part 5 — Maintainability & architecture

### M1. `ExrApp` is the new god object — extract the playback engine (HIGH, L)

`src/app.rs:115`: 78 fields, ~60 methods, 5,700 lines. It owns the playback
engine (playhead, T1 cache, caps, inflight, epoch, watchdog, precache latch,
render-watch — ~15 fields), the decode-worker plumbing, LUT/OCIO state, AND
~1,900 lines of `draw_*`. The engine methods (`pump_decode`, `pump_t2`,
`playback_*`, `tick_*`, `apply_load_result`, `invalidate_inflight`) are almost
entirely egui-free; their only tentacle is `ctx.request_repaint`.

**Extract a `PlaybackEngine` (own module) with repaints behind a small
callback/trait.** The 56 app-level tests already exercise exactly this seam
(they call `tick_*`/`apply_load_result` directly), so the move is
test-protected and mostly mechanical. This is the module boundary that
survives the Qt port (#44): `draw_*` gets rewritten; the engine ships
unchanged. Pair with splitting app.rs into a directory module
(`app/{engine.rs, loading.rs, color.rs, ui/*, tests.rs}`).

### M2. Cache-budget recompute is hidden inside `draw_status_bar` (HIGH, S)

`src/app.rs:2784`: T1 capacity and the T2 enable/cap decision — the logic
preventing RAM/VRAM overcommit — run only as a side effect of painting the
bottom panel, and silently vanish in any UI restructure. Lift into a
`tick_budgets()` called next to `tick_playback`. Do this first; it's the
cheapest piece of M1.

### M3. Dual ownership of viewer prefs, cloned both ways every frame (MED, M)

`diff_colormap`/`diff_metric`/`background`/presets live on both `ExrApp` and
`ExrViewer`, round-tripped per frame at app.rs:3848. Single-owner them on the
viewer with a serde-able `ViewerPrefs` read at `save()` time.

### M4. `draw_canvas_gpu` re-accreted to 507 lines (MED, M)

`src/viewer.rs:2374` — uniform construction, LUT re-bake, ring allocation, a
large closure with `Cell`/`RefCell` plumbing, all six compare modes, wipe
interaction, OCIO emission. Split per the M1-2026-06 playbook
(`build_frame_uniforms`, `DrawCtx` struct replacing the cells,
`emit_mode_draws`); finishing the #114 render-program migration shrinks the
mode arms naturally. Guardrail: the existing kittest
`ui_renders_all_compare_modes_without_panicking`.

### M5. Smaller items
- **Inverted dependency:** `gpu/thumbnail.rs:234` imports pixel helpers from
  `viewer.rs` — the one wrong-direction arrow. Move `thumb_dims`/
  `sample_channel_f32`/`pixel_val` to `render_math.rs` (S).
- **Stale module-wide `#[allow(dead_code)]` + phase comments** in
  lib.rs:17–23, layer.rs:52, render_program.rs — they reference phases that
  have shipped and now mask genuinely dead code (S).
- **T2 ring is the least-tested risky code** (viewer.rs:3001–3101): only the
  victim policy has a unit test; cap-shrink eviction, layer-switch
  invalidation, and pump ordering are untested, and wgpu OOM is
  process-aborting. Factor the ring map policy into a pure struct like
  `FrameCache` and test it (M).
- **Contract drift (docs):** docs/playback README + memory-contract name
  `generate_gpu_texture` (now `prebuild_t2`/`build_layer_texture`);
  hardening-plan says ~77 tests (now ~239). Also: the concurrency contract
  specifies a single-slot priority mailbox but the code uses an unbounded FIFO
  with epoch-skip — near-equivalent for sequence frames, but a mid-playback
  slot-B open queues ahead of the playhead frame (priority inversion, one full
  decode). Either implement the mailbox or document the deviation (S).
- **Memory-contract nits:** T1 eviction is T2-blind (contract says
  T2-built-first); code floors the T1 cap at 2 where the contract says refuse
  — the floor is better, update the doc (S).

## Suggested sequencing

1. **Quick wins, this week (all S, playback-facing):** P1 worker repaint wake
   → P2 deadline scheduling → P3 scrub same-frame guard → F1 histogram
   suppression → M2 budget tick out of the status bar. These five are a
   day-or-two of work and likely transform playback feel.
2. **P4 loop-wrap eviction (M)** with a regression test — kills the wrap
   stutter and decode churn.
3. **Upload-path bundle (U1–U4):** Rgba16Float + f16 fast path + reusable
   staging + byte-budgeted pump. Halves per-frame CPU+bandwidth and doubles
   effective T2 capacity; unlocks linear filtering.
4. **F2 beauty-only scrub, F3 contact-sheet amortization, F4 async
   render-watch** as follow-ups; G1–G6 as a hygiene batch.
5. **M1 engine extraction + app/ split** — schedule as its own PR series
   before starting #44; it's the de-risking groundwork the Qt port needs.

Relation to open issues: P1/P2 revise #100's validation numbers (part of the
measured shortfall was self-inflicted); F2 is a smaller independent lever than
#94; F3/G1 relate to #67 and #112 but are distinct defects; U1–U4 are new
(adjacent to #33 but on the upload side, not decode); M1/M2 are the concrete
pre-#44 architecture work alongside #66.
